# swe-task: synthetic DeepSWE tasks (hengyuf's port of Baihe's pipeline)

This tree runs Baihe's synthetic-DeepSWE task pipeline (`DeepSWE Mid-train Synthetic Data.pdf`) entirely on
hengyuf's resources, with the student switched to a local checkpoint. Ported 2026-10-16 from Baihe's
`/lustre/fsw/portfolios/nemotron/projects/nemotron_evals_research/users/baiheh/swe-task` (code) and his ATP app
`.../baiheh/nano-rl/agent-teacher-pipelines` (probe campaigns). The pipeline code never reads Baihe's tree.
Provenance: `reference/baiheh-swe-task-code-20261016.tar.gz` (his pristine `synth/` and `opensandbox/`) and
`reference/baiheh-runs-20261016/` (his smoke1/val1 summaries and Slurm logs). Interfaces shared by the port's
components: `docs/port-contract.md`.

## Differences from Baihe's pipeline
1. **Student.** `super` (hosted Nemotron 3.5 Super VL) is replaced by `sc14`: the local checkpoint
   `swe-rl-v2-sc-migration/models/swonlysc-step0014/hf`, served as model `policy` by persistent vLLM workers
   (1 node x 8 H100, TP8, RL r2 engine args, `max_model_len` 262144; GPU jobs on `batch`) behind one router per
   synth job (`student/`). The router gives every call the serving semantics of hengyuf's DeepSWE eval with the
   131k cap: temperature 1.0, top_p 1.0 (hosted models: 0.95), `chat_template_kwargs` `enable_thinking: true`,
   `truncate_history_thinking: false`, `max_tokens := min(requested, 131072)`, exact context clamp via
   `/tokenize` on overflow. ATP's Gym model server gives the local student the eval's reasoning handling
   (`preserve_reasoning_in_assistant_content: true`, `sequential_reasoning_allowed: false`): history thinking goes
   back as `<think>R</think>C` in the assistant content, exactly as in its target rollouts, so the router's
   reasoning-field handling (empty ones dropped, `reasoning_content` renamed) only matters for callers that send
   such fields. The router routes by conversation affinity (prefix cache) with a soft in-flight cap per worker
   (`student/README.md`). OpenCode context for the student is 262144 (auto-compaction at 242,144) instead of
   1,048,576, output limit 131072. Rollouts stay in ATP's campaign code; ATP's Gym config reads the router URL from
   `SYNTH_STUDENT_BASE_URL` (`${oc.env:...}` in `synth/settings.json`). A probe or student chat first starts the
   job's router and waits for a routable worker (`SYNTH_STUDENT_WAIT_S`, default 10800 s for probes, cut short so
   that ATP admission still fits before the job's end; 3600 s for chat).
2. **Codex for every agent stage.** The two Cursor stages (task builder `understand` and `instruction_rubric`)
   and the smoke S3 Cursor check now use codex (`gpt-6-astra`, xhigh) - user decision. codex 0.163.0 runs from
   `tools/codex` with a per-job `CODEX_HOME` on node-local scratch seeded from `tools/codex/home/config.toml`;
   only the codex process gets `CODEX_HOME` and `NVHUB_API_KEY`, and its config keeps `*KEY*`, `*TOKEN*`,
   `*SECRET*`, `*PASSWORD*`, `*CREDENTIAL*` out of the commands it runs. Agent environments drop every variable
   whose name contains KEY/TOKEN/SECRET/PASSWORD/CREDENTIAL (Baihe's suffix rule missed `NVAPI_KEY`) and
   `SYNTH_STUDENT_BASE_URL` (the student router is the pipeline's, not the agents'). Prompts, argv, gates and
   thresholds are unchanged.
3. **Credentials.** One hub key: `NVAPI_KEY_NEW` (since 2026-10-17, when `NVAPI_KEY` hit its $5000 budget) from
   `/lustre/fsw/portfolios/nemotron/users/hengyuf/.env` (`synth/common.HUB_KEY`), read at
   call time (Baihe: two keys in `swe-task/.api`). Probes therefore use ATP's single `existing` credential
   (`NVIDIA_API_KEY`) and no `priority_1/priority_2` pool; the local student gets no credential. OpenSandbox
   settings come from `secrets/opensandbox.env` (Baihe: the ATP `.env`); same Cell-3 service.
   `synth/run.sbatch` (`#SBATCH --export=NONE`) unsets secret-looking variables and `SYNTH_STUDENT_BASE_URL` at job
   start.
4. **ATP app copy.** `atp/` replaces Baihe's ATP app (vendored Gym 2f11dec3, its own uv/Python/controller venv,
   `.env` generated by `tools/make_secrets.py`), with the changes the local student needs in 3 scripts (per-model
   endpoint and limits, the eval's reasoning handling for a `local` spec, credential only on hosted URLs) and, since
   2026-11-08 20:51, a 4th: `deepswe_capture.py` writes + fsyncs OpenCode's output stream off the agent event loop
   (a stalled Lustre fsync there dropped every PTY of the process; item 6 of `atp/README.md`); see `atp/README.md`.
   Its `configs/deepswe.json` and `deepswe_campaign.py` are Baihe's, unchanged.
5. **Target rollouts.** `data/targets/sc14-out131k-kimi` replaces the partial-selected super/kimi export: 5 sc14
   rollouts per task from hengyuf's DeepSWE eval (131k per-call cap) and Baihe's 5 selected kimi rollouts
   (`synth/tools/reformat_rollouts.py`; rebuilt 2026-10-16 19:30 PDT by job 20372704). Kimi passes have
   `failing_tests_available: true` (known empty); kimi fails (and the one `grader` slot) carry grade counts but no
   per-test names (`failing tests: unavailable` in transcripts). An sc14 rollout that merely ended on a reasoning
   item has `agent_error` None (an ordinary attempt; ATP has no label for it). sc14 transcripts can contain OpenCode
   compaction `user` messages. `synth/rollouts.target_records()` refuses the dataset until `COMPLETE.json` exists,
   checks `index.json` against `COMPLETE.json` once per process and every record line against `index.json`.
6. **Smaller items.** Gym task-store validation uses hengyuf's swe-rl Gym copy (same commit 17abf2dd as Baihe's);
   CPU jobs run under account `nemotron_agents_dev` (Baihe: `nemotron_n4_post`) with 16 CPU / 96 GB instead of
   Baihe's whole-node `--exclusive` (measured: 0.3 cores avg, 17.5 GB peak), on the partition among cpu_datamover /
   cpu_dataprocessing / cpu_interactive that `tools/pick_partition.py` estimates to start first; official builds
   use 24 h jobs (`tools/launch_build.sh`).

Unchanged: teacher `kimi` and judge `glm` on the NVIDIA inference hub (`reasoning_effort: max`), prompts, gates,
thresholds, OpenSandbox Cell-3, ATP's campaign code for probes, idempotent/resumable stages.

### Bug fix in Baihe's code (2026-10-17)
`task_builder.MATERIALIZE` (the controller script that turns image A + start.patch into the student's starting
state C) ran `git ls-files -o -i --directory | grep -zE '(dist|build|out|lib|...)/$' | xargs rm -rf` under
`set -euo pipefail`. When the repository has no such ignored build directory, grep exits 1 and the whole script
exits 1 without output, so every candidate fails at materialize. val1's risor happened to have an ignored `out/`;
official1-bandit (klen/pylama) and official1-narwhals (ibis) do not (reproduced with `bash -x` in sandboxes from
their image A snapshots). Fix: `{ grep ... || true; }`. Recovery of an affected build: rename the failed
`cand-*/stage.json` and `summary.json` aside and rerun the build; the authored patches are reused.

### Second fix (2026-10-17): reversed patch labels
codex sometimes writes patches with `git diff -R`-style labels (`diff --git b/X a/X`, `--- b/X`, `+++ a/X`).
`git apply` accepts them, so the gates pass, but the DeepSWE grader's `patch_paths` finds no file in such a test.patch:
`grader.py prepare` then never resets an agent's edits to those test files before applying test.patch (official1-
narwhals cand-c02: 6/10 rollouts "test.patch failed to apply" -> infra; a non-conflicting edit would even leave
agent-modified tests in the grading), and the author check's solution/test overlap test sees nothing. Fix in
`task_builder.py`: `canonical_labels` relabels author patches to a/ -> b/ before validation (hunks unchanged; applies
identically), and the gates reject a test.patch with paths the grader cannot parse (`unseen_paths`). The grader
itself stays DeepSWE's, byte-identical.

### Evolution seeds by validity, not pass rates (2026-10-17, hengyuf's rule)
Baihe's `build()` evolved every round-0 task that was not accepted, whatever the reason, so a task with broken
grading (narwhals cand-c02, inconclusive) seeded 5 branches, and accepted tasks never did. Now (`task_builder.seed_check`,
`valid_seeds`, written to `<round>/seeds.json`):
1. Only tasks that passed the gates are probed, i.e. the reference solution passes every F2P and P2P test under the
   real grader (3 runs + the final check); others are never rolled out or evolved (unchanged).
2. After the probe, a task is invalid if any rollout's verifier produced no grade (tests could not be applied or run;
   `metrics.json` `grading_failures`) or it has < 3 valid rollouts per model. Transient platform failures (5xx,
   timeouts, sandbox capacity) are retried by ATP; a hub 4xx (e.g. 422 budget_exceeded) makes the slot fatal, and a
   task left with < 3 valid rollouts becomes an invalid seed. So the builds must stop BEFORE the hub key runs out:
   `tools/hub_budget.py --min-remaining 500` (exit 3 = stop; the watchers run it every poll).
   - (2026-10-20, official1-wasmi c05 kimi-r3: "os error 5" reading the cargo registry and rustc SIGBUS in the verifier
     sandbox, so `[gate] build` failed, F2P 0/17, P2P 0/394, and ATP recorded a completed FAIL without retry) score()
     counts a FAIL as infra when nothing in F2P and P2P passed and the logs of its last grading attempt
     (`grading/attempt-<n>/{run,stdout,stderr}.log`) show Input/output error, os error 5/28, EIO, ENOSPC, SIGBUS, Bus
     error or "No space left on device" (`rollouts.verifier_fault`): status infra, so the slot is out of the rates and
     `valid`, with the reason in the record's `verifier_fault` (its own line in rollouts/<slot>.md) and in metrics
     `verifier_faults`. Main's decision (2026-10-20, backups `*.pre-vfault-seed`): a platform fault like PTY/410/422,
     NOT a grading failure (`grading_failures` stays task-caused; the slot keeps ATP's verifier_error, so
     tools/recover_slots.py sees a retryable loss): the task stays a valid seed unless a model drops below 3 valid
     slots. probe_records() is unchanged (ATP's view: grading_repair and regrade compare it with score()'s rendered
     rollouts). Of 6,405 graded attempts of all runs, 19 had nothing passing and only that slot matches. New
     and resumed builds only: the live wasmi job scores c05 with the old code (kimi-r3 a FAIL).
3. Round 0: every valid task seeds `branches` children, accepted ones included. Later rounds: each lineage continues
   from its best valid non-accepted child (ranking unchanged); a lineage without one stops.
4. Acceptance is unchanged (sc14 <= 0.2, clean kimi >= 0.6, similarity >= 6). The evolve prompt tells an accepted
   parent's branches to keep what made it work (`evolve_outcome`); a rejected parent's prompt text is unchanged.
official1-narwhals: c02 dropped as a seed (6 grading failures), c04 (accepted) added; its old round-1 probe
(`probe-7f97a213`, with the c02 children) is abandoned and a new one is created. official1-bandit: same seeds as before.

### Third fix (2026-10-18): authors are told that build outputs are deleted
MATERIALIZE deletes git-ignored build outputs (dist/build/out/lib/coverage/..., *.tsbuildinfo) so compiled copies of
the masked code cannot leak, but `prompts/author.md` never said so: the authors' self-checks ran on A (outputs
present), and in official1-vitest (jestjs/jest monorepo) 2 of 5 round-0 candidates died in the gates with
"Cannot find module /app/packages/jest-cli/build/index.js". The prompt now states the deletion, requires
`run_tests.sh` to rebuild what the tests import, and makes the self-check start with the outputs deleted.
render() reads the prompt per call, so running builds pick it up for their next authoring.

### Fourth fix (2026-10-18): skipped tests are not failures in the gates
`calibrate()` treated every non-passed base-suite test of the starting state as broken, so environment SKIPS (aiohttp
on Python 3.12: partitioned-cookie and pre-3.11 SSL tests) produced "base suite fails on the starting state": 16 of 25
official1-httpx round-1 branches lost attempt 0 and 2 were lost for good. Now only 'failed' counts. A new-suite test
is unstable only if it fails, or skips in some solution runs and passes in others; skipped tests enter neither P2P
nor F2P (unchanged). Lost branches can be recovered by moving their stage.json aside and resuming, so the gates re-run
on the cached author output.
- (2026-10-20, official1-dynamodb) build_env's exclusions stay out of P2P: its run_tests.sh excluded 3 wall-clock
  'timeout' tests (<= +50 ms) with Jest --testNamePattern, round-1 authors' RUN TESTS ran them, and 23 of 25 tasks
  graded them P2P. `task_builder.env_unreliable` takes the tests that every env baseline reporting them shows skipped,
  or that passed in only one; `calibrate(..., unreliable)` keeps them out of P2P and out of "base suite fails" (IDs
  matched across report formats by file and title words, `env_matches`); gates JSON `env_excluded`. The env stage
  records no exclusion list: stage.json "flaky" holds A/B flips only, the reasons are free text (result.json "summary",
  run_tests.sh comments), and deselecting filters (pytest -k, go -run/-skip, nextest) leave no trace in the reports.
  Recomputed from the saved gate reports: all 30 built dynamodb candidates lose exactly those 2-3 tests (6 ID formats),
  no candidate of any other run loses any. New and resumed builds only (dynamodb's tasks keep them).

### Fifth issue (2026-10-18): RUN TESTS blocks must never exit early
After the third fix asked `run_tests.sh` to rebuild, some round-1 authors (official1-vitest: 6 of 15) gated the
suites on a rebuild/typecheck with `exit "$rc"`. A student solution that does not build then leaves no report at
all ("Verifier did not produce /logs/verifier/reward.json"), which counts as an ungraded infra slot instead of a FAIL
(c04-r1b1: 4 of 5 sc14 slots) and makes the task itself defective as RL data. `prompts/author.md` now forbids early
exits and requires build/typecheck steps to be recorded as `[gate]` pass-to-pass tests. DONE for official1-vitest
(hengyuf's rule: a solution that does not build or typecheck is FAILED): `synth/tools/regrade.py repair --gate` gave the
8 affected blocks a `[gate] <build> && yarn build:ts` P2P test, validated each with the real grader (reference 1, empty
0, syntax error 0, type-only error 0), regraded the 7 lost slots (all FAIL) and re-scored: c05-r1b2 newly accepted, so
official1-vitest has 4 accepted tasks; all four fail a non-compiling or non-typechecking solution. Logs:
`<build root>/early-exit-fix.jsonl`, `early-exit-fix-logs/`, backups in `early-exit-fix-backups/`.

### hengyuf's decisions of 2026-10-18 (pipeline rules)
- Hidden tests (`prompts/author.md`): two kinds only. (a) Failure-pattern tests pin down the behaviour behind the
  target failure pattern(s) this task must trigger; they belong in the hidden tests even where the instruction only
  implies that behaviour. (b) Every other hidden test checks only functionality the instruction states. Both go
  through the public interface (no private names or other implementation details a correct solution may choose).
- Leak scan (`task_builder.leak_tokens` / `leak_problems`): comment, docstring, parameter/field-declaration and
  import lines are no longer "distinctive" (litestar's new decorators repeat their siblings' docstrings and
  parameter lists: 3 correct fastapi branches were rejected), and a leak needs at least half (>= 3) of one solution
  file's distinctive lines inside ONE window of a file as long as that solution file's added code (>= 60 lines),
  i.e. one place reproducing the implementation, not lines scattered over a whole file.
- Early-exit tasks of official1-vitest (DONE 2026-10-18 with `synth/tools/regrade.py`; every change logged in
  `<build root>/early-exit-fix.jsonl`, backups `*.pre-early-exit-fix` / `*.pre-gate-fix`): the 8 RUN TESTS blocks
  that exited on a failed rebuild/typecheck (c01-r1b2/b4, c04-r1b0/b1/b2/b4, c05-r1b0/b2) no longer exit, and (user:
  a solution that does not build or typecheck FAILS, as in the DeepSWE frame) each records that step as the P2P test
  `[gate] <cmd> && <cmd>` in the base report (`repair --gate`, the convention of the sibling blocks c01-r1b0/c01-r1b3/
  c04-r1b3/c05-r1b3). Jest's `yarn build:js` only strips types, so the 5 blocks that rebuilt JS only gate
  `yarn build:ts` too. All 8 pass `validate --gate` (reference 1; empty 0; syntax error and type-only error both 0
  through the gate). The 7 lost sc14 slots all grade FAIL through the gate (c04-r1b1: jest-worker test typecheck;
  c05-r1b2, c04-r1b2: `yarn build:ts`): c05-r1b2 newly ACCEPTED (sc14 0.2, kimi 1.0, similarity 7), c04-r1b1 rejected
  (sc14 0.2, kimi 1.0, similarity 4), c04-r1b2 rejected (0.0/0.0). All 35 passing rollouts of the 5 tasks that gained
  `yarn build:ts` still pass, so accepted c04-r1b0 and c05-r1b0 are unchanged. official1-vitest: 4 accepted.
- Broken test setups (2026-10-18, official1-arcane cand-c04: hidden tests re-homed in a new Go file collided with the
  students' same-named tests, so every rollout scored F2P 1/22, P2P 126/431): author.md now requires removed tests
  to go back into their original files, and `task_builder.uniform_failure` (metrics field) makes such a task an
  invalid seed when every graded rollout with a patch (>= 4) scores the same F2P and P2P with P2P short. Its
  round-1 branches in official1-arcane were pre-blocked with failing stage.json markers (old-code job).
  The gates also reject the layout statically (`task_builder.rehomed_go_tests`): a Go test function removed by
  start.patch from file X and re-added by test.patch in another file of the package while X is untouched
  (found by the arcane watcher; latent in cand-c02, where no rollout happened to trigger it).
- Gate timeouts (2026-10-18 21:5x, found by the arcane watcher): after the gate rule, round-1 authors wrapped COLD Go
  compiles and suites in short `timeout 300s go build ...` commands (MATERIALIZE purges the build cache; verifiers have

## Known differences and risks
a. **sc14's probes vs its targets.** sc14's target rollouts come from hengyuf's DeepSWE eval; its probes (like kimi's
   targets and probes) run in ATP's harness, which treats student and teacher alike. Remaining differences:
   - sandbox: ATP gives every agent sandbox 4 CPU / 16 GiB guaranteed (task resources x2, requests = limits); the
     eval used limits of 4 CPU / 32 GiB with requests of 0.5 CPU / 512 MiB (burstable). kimi's targets were made
     under ATP's 16 GiB; kept identical for student and teacher on purpose;
   - agent time: ATP gives OpenCode min(10800 s, job deadline - now); the eval 10800 s;
   - a prompt of >= 262144 tokens: ATP turns vLLM's 400 into an empty `length` reply or marks the slot `fatal` (the
     eval's model server propagates the error). Never happened in the 565 eval rollouts;
   - OpenCode 1.17.11: ATP downloads the `-baseline` release build, byte-identical to the RL/eval binary (sha256
     `0254a429…`);
   - serving: vLLM seed = job id (eval: 0), and a routed, changing fleet of workers instead of one fixed replica
     (a conversation that moves to another worker loses its prefix cache).
b. **One hub key.** Baihe's runs used three credentials (ATP `existing` + `.api` `priority_1`/`priority_2`); here
   everything uses the single hub key (`NVAPI_KEY_NEW`). ATP's admission throttling for kimi is therefore model-wide instead of
   per credential, and codex, glm and `chat()` share that key's quota with the probes.
c. **codex.** 0.163.0 through the NVIDIA hub (`openai/openai/gpt-6-astra`, xhigh) with a clone of codex's built-in
   model metadata (`tools/codex/catalog`); Baihe used an OpenAI login, version unknown. The codex package ships

   (`.agents/skills`: karpathy-guidelines, repo-orient); the other two (hsg-nano-experiments, slurm-job) were never
   opened in his runs.

   with these targets that is not literally true (sc14: the eval; kimi: ATP's export). The prompt is unchanged.

     rotate the keys it holds;
