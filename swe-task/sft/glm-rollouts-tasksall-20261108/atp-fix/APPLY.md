## The change

* `scripts/deepswe_capture.py` (+32/-2, marked `# hengyuf:`): `run_opencode.drain()` keeps the same per-chunk
  `stream.write` + `os.fsync`, but runs them in a dedicated `ThreadPoolExecutor` (`_STREAM_IO`, at most 32 threads named
  `atp-stream-io_N`, started on demand) through `_in_stream_io()`. That helper awaits the call. If the drain is
  cancelled, once or several times, it first waits for the in-flight write + fsync to finish and then re-raises
  `CancelledError`. So the file (closed by the drain's `with`) is never closed under a write, and a chunk read from the
  PTY is always written. When not cancelled, errors propagate as before (same exception object). Bytes, order, file
  names, eager open, per-chunk durability, `capture_protocol_version` and all function signatures are unchanged. The
  open/close of the two files and all per-attempt lifecycle writes stay synchronous (unchanged).
  The comment deliberately contains `glm-rollouts-sftv3 capture_patch.py`: the read-only sftv3 patcher (used by the
  sftv3 infra re-run, job 21541211) then reports `already` instead of raising "drain() block not found".
* `upstream/deepswe_capture.py`: new; `cp -p` of Baihe's original (sha256 `b1babe29...`, mode 0444, Baihe's mtime).
* `hengyuf-changes.diff`: regenerated by the same method (3 comment lines + `diff -ru a/scripts b/scripts` over plain
  copies of the 29 `*.py`); now 4 scripts, +75/-17. The other three scripts' hunks are byte-identical to the current
  diff apart from the `---`/`+++` copy timestamps. It has been verified to apply with `patch -p1 --fuzz=0` to Baihe's
  scripts and to reproduce all 29 app scripts.
* `PROVENANCE.json`: updated (same format, round-trip checked):
  * `files["scripts/deepswe_capture.py"]`: `current_sha256` and `modified_by_hengyuf: true`;
  * `upstream_pristine_copies["upstream/deepswe_capture.py"]`;

  * `tools["tools/check_hengyuf_changes.py"].sha256` and `updated_at`.
* `README.md`: the change counts, the `upstream/` description, a note on frozen snapshots, item 6, and the offline check
  command.
* `tools/check_hengyuf_changes.py`: new offline `capture` subcommand, about 20 s. The `http` and `config` code is
  unchanged; only the argparse choices and dispatch were edited.
* `T/capture_patch.py` (tasksall): keeps OLD/NEW/MARK and `patch_file` byte-compatible with sftv3's. Outcomes:

## Before installing

1. Read-only state check (no writes): `$PY -I -B $F/install.py check`. Every line must read `pre-install` (`absent` for
   the new upstream copy) or `installed`, and the output must end with `OK check`.
   * If a target reads `changed:<sha>`, someone edited it after staging. Do not install. Rebuild instead (see "Rebuild"
     below).
   * If a staged file differs from the manifest, it was edited after the build. Rebuild as well.
2. Running jobs. Check them in a standalone call (`squeue -u hengyuf`); this workflow ran no Slurm commands. Installing
   while jobs run is safe:
   * every file is replaced by one atomic rename, so a concurrent `stage()` copytree sees either the old or the new
     file;
   * a job that has already staged keeps its job-local copy until it ends;
   * the sftv3 re-run (job 21541211, read-only sftv3 patcher) reports `patched` if it stages before the install and
     `already` after it. Both were tested and both run the fix;
   * tasksall legs report `patched` (old patcher on the old app), `already` (old patcher on the new app) or `upstream`
     (new patcher on the new app);
   * the manifest order installs the app files first and the tasksall patcher last.

## Install

```bash
F=/lustre/fsw/portfolios/nemotron/users/hengyuf/swe-task/sft/glm-rollouts-tasksall-20261108/atp-fix
A=/lustre/fsw/portfolios/nemotron/users/hengyuf/swe-task/atp
T=/lustre/fsw/portfolios/nemotron/users/hengyuf/swe-task/sft/glm-rollouts-tasksall-20261108
PY=$A/runtime/controller/bin/python
$PY -I -B $F/install.py check && $PY -I -B $F/install.py install
```

`install.py install` first re-checks every staged sha256 and mode and every target's pre-install sha256. If anything
is unexpected it refuses before writing anything. Then, for each entry in table order, it:

1. copies the staged file to `<target dir>/.<name>.atp-fix-new` (this name cannot match `scripts/*deepswe*.py`, which
   `freeze_source` globs);
2. sets the table's mode and the staged mtime (as `cp -p`; so `upstream/` keeps Baihe's mtime);
3. fsyncs the copy and verifies its sha256;
4. `os.replace`s it over the target and fsyncs the directory.

Entries already installed are skipped, so re-running after an interruption is safe. It ends with `verify`.

Manual equivalent for one entry (repeat in table order with that row's values; stop at the first error):
```bash
s=$F/app/scripts/deepswe_capture.py; t=$A/scripts/deepswe_capture.py; mode=0644
want=<staged sha256>; pre=<expected pre-install sha256>     # pre=absent: `test ! -e $t` instead of the next line
echo "$pre  $t" | sha256sum -c --quiet
tmp=$(dirname $t)/.$(basename $t).atp-fix-new
cp -p $s $tmp && chmod $mode $tmp && echo "$want  $tmp" | sha256sum -c --quiet && mv -f $tmp $t
```

## Rollback

```bash
$PY -I -B $F/install.py rollback
```

Rollback works in reverse order:

* each target that still has the installed sha256 gets its pre-install bytes and mtime back from `F/rollback/` (mode
  0644), via the same temporary file and rename;
* `upstream/deepswe_capture.py`, which did not exist before, is removed;
* a target that is already back in its pre-install state is skipped;
* if any target is in a third state (edited after the install), the rollback refuses without writing anything.

Jobs that staged in between keep their staged copy. The next staging after a rollback gets Baihe's drain again, and the
restored tasksall patcher (the sftv3 copy) patches it as on 11-07.
